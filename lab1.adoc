==  Этапы разработки ПО и парадокс квалификации

[arabic]
====
1. *Придумываем что делать* (Анализ требований) +
   Заказчик говорит "хочу вот это", а мы разбираемся:
   - Что именно нужно сделать
   - Какие функции важны
   - Какие ограничения есть

2. *Рисуем схему* (Проектирование) +
   Senior-разработчики создают "чертёж" системы:
   - Из каких частей будет состоять программа
   - Как они будут между собой общаться
   - Какие технологии использовать

3. *Собираем конструктор* (Реализация) +
   Младшие разработчики по готовой схеме пишут код:
   - Делают отдельные кусочки программы
   - Соединяют их вместе
   - Как строители по готовому проекту дома

4. *Проверяем на ошибки* (Тестирование) +
   QA-инженеры ищут баги:
   - Ломают программу разными способами
   - Проверяют, всё ли работает как задумано
   - Как тестеры новых автомобилей

5. *Чиним и улучшаем* (Поддержка) +
   После запуска программы:
   - Исправляем найденные ошибки
   - Добавляем новые функции
   - Как сервисное обслуживание машины после покупки
====

*ВАЖНО:* этапы часто повторяются по кругу

=== Почему код пишут "младшие" разработчики?


[arabic]
====
. *Экономическая эффективность* +
   Senior-разработчики стоят дороже — их время разумнее тратить на сложные архитектурные задачи, а не на рутинный код.

. *Обучение на практике* +
   Написание кода под контролем seniors — лучший способ для juniors/middles набраться опыта.

. *Оптимизация процессов* +
   Распределение задач по уровню сложности:
   - *Seniors*: проектирование, код-ревью, решение сложных проблем
   - *Juniors/Middles*: реализация готовых решений

. *Мотивация* +
   Возможность писать production-код даёт младшим разработчикам ощущение вклада в проект.
====
*ВАЖНО*: строгий код-ревью от старших коллег, иначе качество кода может пострадать.

== Запуск `main()` в микроконтроллере

=== Этапы инициализации перед `main()`

В микроконтроллерах (МК) выполнение программы начинается с аппаратного сброса и проходит через несколько ключевых этапов:

[arabic]
====
. *Сброс (Reset Handler)* +
   - Процессор начинает выполнение с *вектора сброса* (обычно `0x00000000`)
   - Выполняется `Reset Handler` - стартовый код (часто на ассемблере)

. *Инициализация стека* +
   Установка начального значения указателя стека (SP) из предопределённой области памяти

. *Копирование данных в RAM* +
   Инициализированные статические/глобальные переменные копируются из Flash в RAM

. *Обнуление .bss-секции* +
   Область для неинициализированных глобальных переменных заполняется нулями

. *Настройка тактирования* +
   Активация тактовых сигналов для CPU и периферии (PLL, делители частоты)

. *Инициализация периферии* +
   Ранняя настройка критичной периферии (watchdog, FPU, DMA)

. *Конструкторы глобальных объектов (C++)* +
   Вызов конструкторов глобальных объектов (если используются)

. *Переход в `main()`* +
   Управление передаётся в функцию `main()`
====

=== Вывод

В микроконтроллерах `main()` - лишь точка входа пользовательского кода. +
Реальное выполнение начинается с аппаратного сброса, настройки памяти и периферии. +
Процесс зависит от архитектуры МК, но общая логика сохраняется.

== Почему 12, а не 13?

=== Код программы

[source,cpp]
----
#include <iostream>

int Increment(int value)
{
    static int result = value; // Инициализация происходит ТОЛЬКО при первом вызове
    result++;
    return result;
}

int main()
{
    auto result = Increment(10);
    std::cout << "result == " << result << std::endl; // 11

    result = Increment(12);
    std::cout << "result == " << result << std::endl; // 12
}
----

=== Почему выводится 12, а не 13?

*Статическая переменная* `result` ведёт себя особым образом:

[arabic]
====
. При *первом вызове* `Increment(10)`:
   - Переменная `result` инициализируется значением 10
   - Затем увеличивается до 11 (10 + 1)
   - Возвращается 11

. При *втором вызове* `Increment(12)`:
   - Инициализация `static int result` ПРОПУСКАЕТСЯ (она работает только один раз)
   - Переменная `result` сохраняет своё предыдущее значение 11
   - Увеличивается до 12 (11 + 1)
   - Возвращается 12
====

=== Наглядная таблица выполнения

[cols="1,2,2,2", options="header"]
|===
| Вызов | Параметр | Значение result | Возвращаемое значение
| 1-й | 10 | Инициализация = 10 → 10+1 = 11 | 11
| 2-й | 12 | Пропуск инициализации → 11+1 = 12 | 12
|===

=== Как получить 13?

Если нужно, чтобы каждый вызов учитывал новый параметр:

[source,cpp]
----
int Increment(int value)
{
    static int result = 0; // Инициализация нулём
    result = value; // Присваивание при каждом вызове
    result++;
    return result;
}
----

Теперь второй вызов `Increment(12)` даст 13, так как:
1. `result` сохраняется между вызовами, но
2. Мы явно обновляем его значение параметром

=== Вывод


Статические переменные внутри функций:

====
* Инициализируются только один раз

* Сохраняют значение между вызовами

* Могут приводить к неочевидным результатам, если не учитывать их особенность
====

== Общий вывод

Из того, что я узнал можно сделать несколько важных выводов о разработке ПО и работе программ:

====
1. *Разработка - это процесс* +
   Создание программы похоже на строительство дома:
   - Сначала нужно понять, что строим (анализ)
   - Потом сделать чертёж (проектирование)
   - Затем построить (реализация)
   - Проверить качество (тестирование)
   - И постоянно ухаживать (поддержка)

2. *Команда работает как механизм* +
   - Опытные разработчики (seniors) создают "чертежи" и решают сложные задачи
   - Младшие (juniors/middles) воплощают эти идеи в код
   - Так получается эффективно и выгодно

3. *Программа - не просто main()* +
   Даже простая программа перед запуском:
   - Компилируется в несколько этапов
   - В микроконтроллерах проходит сложную инициализацию
   - Это как "невидимая" работа, которая делает возможным выполнение нашего кода

4. *Мелочи имеют значение* +
   Пример с функцией "*12, а не 13*" показывает:
   - Кажущиеся простыми вещи (как static переменные) могут вести себя неочевидно
   - Важно точно понимать, как работает язык программирования
   - Одна маленькая особенность может изменить результат работы программы
====

*Качественное ПО требует:*

- Чёткого плана и разделения задач в команде

- Понимания всех этапов создания программы

- Внимания к деталям реализации

- Постоянного тестирования и улучшения
